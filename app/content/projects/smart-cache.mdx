# Objetivo general

El proyecto tuvo como propósito desarrollar una solución de backend con enfoque en rendimiento, escalabilidad y despliegue en la nube. La idea principal era migrar grandes volúmenes de datos, exponerlos mediante una API segura y optimizada, y mejorar la experiencia de consulta mediante una estrategia de caché con invalidación automática.

# Fase 1: Preparación y migración de datos

El primer paso fue construir la base de datos en la nube que alimentaría la plataforma. Para esta prueba se utilizó el dataset de Spotify Tracks DB, disponible en Kaggle y con más de 200 mil registros, lo que lo hacía adecuado para evaluar rendimiento y comportamiento bajo carga.

La migración se realizó mediante Azure Data Factory. El proceso consistió en:

- Subir el archivo CSV a Azure Blob Storage
- Extraer los datos desde el almacenamiento
- Transformarlos según el formato requerido
- Cargar la información en una tabla específica de Azure SQL Database

Este punto fue clave, porque estableció la base para el servicio de consulta y análisis posterior.

# Fase 2: Desarrollo de API y autenticación

Una vez almacenados los datos, se desarrolló la API con FastAPI, aplicando buenas prácticas de backend y seguridad. La solución se integró con Firebase para manejar aspectos de autenticación y autorización, además de ofrecer endpoints para consultar, filtrar y registrar información.

Las principales tecnologías en esta fase fueron:

- FastAPI
- Python
- Firebase
- Azure SQL

# Fase 3: Monitoreo de rendimiento

Para observar el comportamiento de la API en producción, se incorporó Azure Application Insights. Esta herramienta permitió recoger telemetría, tiempos de respuesta, trazas de solicitudes y errores en los endpoints. Gracias a esto, fue posible identificar cuellos de botella y evaluar el impacto de la caché en la latencia.

# Fase 4: Implementación de caché con Redis

La parte más relevante del proyecto fue la implementación de una capa de caché con Redis para optimizar las consultas más pesadas. El endpoint `/features` devolvía los primeros 100,000 registros de la tabla `spotify.features`, aproximadamente 15 MB de información. Sin cacheo, esta respuesta podía resultar costosa tanto en tiempo como en uso de recursos.

La estrategia consistió en guardar la respuesta completa bajo la clave:

```text
spotify:features:all
```

Cuando el endpoint era consultado por primera vez, se realizaba la carga desde la base de datos y se almacenaba en caché. Las llamadas posteriores verificaban la existencia de la clave y devolvían la respuesta desde Redis, reduciendo significativamente el tiempo de respuesta.

La misma lógica se aplicó a consultas filtradas mediante el endpoint:

```text
/features/custom?arg=Pop
```

En ese caso, la respuesta se cacheaba con una clave basada en el argumento recibido, por ejemplo:

```text
spotify:features:Pop
```

# Fase 5: Invalidación automática del caché

El sistema también implementó una política de invalidación para mantener la consistencia de los datos. Las claves de caché tenían un tiempo de expiración de 3600 segundos, equivalente a una hora. Además, cuando se agregaba un nuevo registro a través del endpoint `/features/new`, se eliminaban las claves relacionadas con ese género para evitar devolver datos desactualizados.

Por ejemplo, si se enviaba un registro con el género `Dance`, se eliminaba la clave:

```text
spotify:features:Dance
```

Esto aseguraba que la siguiente consulta filtrada por ese género volviera a generar la respuesta desde la base de datos y la volviera a cachear con la información actualizada.

# Fase 6: Despliegue en la nube con Docker

La aplicación fue empaquetada en un contenedor Docker para facilitar su despliegue en Azure Container Registry. El Dockerfile configuraba el entorno necesario, instalaba dependencias y exponía el puerto del servicio.

Ejemplo de configuración:

```dockerfile
FROM python:3.10-slim
WORKDIR /app
RUN apt-get update && \
    apt-get install -y curl apt-transport-https gnupg gcc g++ make && \
    curl https://packages.microsoft.com/keys/microsoft.asc | apt-key add - && \
    curl https://packages.microsoft.com/config/debian/10/prod.list > /etc/apt/sources.list.d/mssql-release.list && \
    apt-get update && \
    ACCEPT_EULA=Y apt-get install -y msodbcsql17 && \
    apt-get clean && \
    rm -rf /var/lib/apt/lists/*
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN test -f .env && rm .env || echo "no .env file found"
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Posteriormente, la imagen se empujó al registro de contenedores de Azure con el comando:

```bash
docker push acrapicache.azurecr.io/api-cache:latest
```

# Endpoints relevantes

## Seguridad

```text
{domain}/signup
{domain}/login
```

- `POST`: registro de usuario
- `POST`: inicio de sesión y obtención de token

## Recursos

```text
{domain}/features
{domain}/features/custom?arg=genre
{domain}/features/new
```

- `GET`: devuelve los primeros registros de la tabla
- `GET`: devuelve una respuesta filtrada por criterio
- `POST`: crea un nuevo registro en la base de datos y requiere autenticación

## MISC

```text
{domain}/
{domain}/api/version
```

- `GET`: saludo de la API
- `GET`: versión actual del servicio
