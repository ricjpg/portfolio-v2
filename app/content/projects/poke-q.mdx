# Objetivo general

Este proyecto tuvo como finalidad extender y modernizar una aplicación base, incorporando nuevas funcionalidades para demostrar la capacidad de adaptar y mejorar un sistema ya desplegado en Azure, manteniendo su disponibilidad y funcionalidad en producción.

## Contexto tecnológico

- Frontend: Next.js con React
- Backend: API desarrollada en Python con FastAPI desplegada en Azure App Service
- Procesamiento asíncrono: Azure Functions con Queue Trigger
- Base de datos: Azure SQL Database
- Almacenamiento de archivos: Azure Blob Storage
- Mensajería: Azure Queue Storage
- API externa: PokeAPI
- Infraestructura como código: Terraform

# Solución implementada

La aplicación permite generar reportes relacionados con Pokémon, gestionarlos en una cola de trabajo y procesarlos de forma asíncrona para producir archivos CSV con información enriquecida. El sistema se compone de una interfaz, una API REST, una base de datos y funciones serverless que responden a eventos de cola.

## Eliminación completa de reportes

Para soportar la eliminación de reportes, se implementó un endpoint encargado de validar la existencia del registro solicitado y, en caso afirmativo, ejecutar la lógica de borrado. Esta acción no solo elimina el dato en la base de datos, sino que también publica un mensaje en la cola de eliminación.

El worker asociado recibe este mensaje y elimina físicamente el archivo correspondiente en Azure Blob Storage mediante el SDK de Azure. Este enfoque garantiza un flujo consistente entre la base de datos y el almacenamiento de archivos.

## Enriquecimiento del reporte con información detallada

El primer flujo de la API se basaba en la consulta del tipo de Pokémon para obtener una lista general de entidades. Sin embargo, ese conjunto inicial no incluía información detallada como estadísticas base o habilidades. Para resolver esto, se combinó la información de dos endpoints distintos:

1. Endpoint de tipo:

```http
GET https://pokeapi.co/api/v2/type/{type}
```

2. Endpoint de detalle del Pokémon:

```http
GET https://pokeapi.co/api/v2/pokemon/{id}
```

La información original incluía elementos como el nombre, la URL y el slot de cada Pokémon. Luego, se realizaban solicitudes adicionales para obtener atributos más útiles para la generación del reporte, como:

- Estadísticas de combate: HP, ataque, defensa, velocidad y especiales
- Habilidades: nombre, ocultas y cantidad
- Resumen estructurado para exportar a CSV

### Aplanamiento de datos

Un problema importante fue la estructura anidada de la respuesta de la API. Los datos de estadísticas y habilidades venían en formato de diccionarios y listas, lo que complicaba la generación de tabulados y archivos CSV. El proceso de normalización consistió en transformar esos datos a una estructura plana y ordenada.

Por ejemplo, las estadísticas se convirtieron en columnas independientes del DataFrame:

```python
for stat_item in pokemon_data["stats"]:
    stat_name = stat_item["stat"]["name"]
    base_stat = stat_item["base_stat"]
    flat_data[stat_name] = base_stat
```

Este enfoque permitió que campos como `hp`, `attack` o `speed` fueran tratados como columnas directas del dataset.

En el caso de las habilidades, se expandieron de forma horizontal para manejar la variabilidad en la cantidad de habilidades por Pokémon:

```python
abilities = extract_abilities(pokemon_data["abilities"])
for i, ability in enumerate(abilities, 1):
    flat_data[f"ability_{i}_name"] = ability["name"]
```

Además, se agregaron columnas resumen para mantener contexto útil, como:

```text
all_abilities
total_abilities
```

Con esto, cada registro quedó listo para ser exportado a un CSV con una estructura clara y consistente.

### Organización del dataset

Se definió un orden lógico para las columnas del reporte:

1. Identificación: nombre, URL
2. Estadísticas principales
3. Resumen de habilidades
4. Detalles adicionales de habilidades

Esto mejora la legibilidad del archivo y facilita el análisis posterior con herramientas como Pandas o Excel.

## Generación de reportes con muestreo aleatorio

Se incorporó la posibilidad de definir un número máximo de registros aleatorios para incluir en cada reporte. Esta funcionalidad se implementó tanto en el frontend como en el backend.

### Frontend

Se utilizó un componente de entrada para recibir el tamaño de la muestra desde la interfaz del usuario.

### Backend

El endpoint de solicitud fue ajustado para recibir un parámetro de muestreo. Además, el modelo de datos se actualizó para incluir `sample_size`, con validación para aceptar únicamente valores enteros mayores o iguales a cero.

La lógica del worker verifica si la cantidad solicitada es menor que la cantidad total disponible del tipo consultado. Si es así, se extrae un subconjunto aleatorio antes de generar el DataFrame final. Cuando el valor solicitado supera la disponibilidad, se devuelve la lista completa.

## Resultado final del reporte

El CSV final queda estructurado de esta manera:

