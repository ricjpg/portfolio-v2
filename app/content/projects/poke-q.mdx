# Objetivo General

Es extender y adaptar esta aplicación base, añadiendo nuevas funcionalidades y demostrando tu habilidad para modificar y mejorar un sistema existente que debe permanecer desplegado y funcional en Azure.

## Contexto Tecnologico

- **Frontend:** Next.js (React)
- **Backend:** API Python con FastAPI desplegada en Azure App Service
- **Proceso Asíncrono:** Azure Functions (Python Queue Trigger)
- **Base de Datos:** Azure SQL Database
- **Almacenamiento:** Azure Blob Storage (para los CSV)
- **Mensajería:** Azure Queue Storage (para mensajes)
- **API Externa:** PokeAPI
- **Infraestructura como Código (IaC):** Terraform (implícito por la mención del repositorio)

# Tarea 1: Implementar Eliminación Completa de Reportes

El primer paso para implementar la eliminación fue crear el correspondiente endpoint:

```text
{domain}/api/request/{id} <- METHOD_POST (Para el registro)
```

Ese endpoint toma el `id` y hace una búsqueda en la base de datos para verificar si el registro existe. Si existe, ejecuta un método que realiza una consulta para eliminarlo. Este método también envía un mensaje a la cola `DeleteQueue`. Después, el worker o Azure Function llamado `serverless-pokeq-dev` recibe el mensaje y procede a eliminar el archivo del Blob Storage mediante el método `.delete_blob()`, incluido en el SDK de Azure.

# Tarea 2: Enriquecer Reporte con Detalles del Pokémon

Al principio, el funcionamiento de la API era el siguiente:

```http
GET https://pokeapi.co/api/v2/type/{type}
```

En este endpoint, el parámetro `{type}` es el tipo de Pokémon del cual queremos obtener la lista. La consulta devuelve la siguiente información:

1. **Nombre del Pokémon**
2. **URL del Pokémon**
3. **Slot**

Para el nuevo funcionamiento, se necesitaban extraer datos de la API de Pokémon desde dos estructuras diferentes:

1. **Lista básica:** contiene nombres y URLs de Pokémon.

   ```http
   GET https://pokeapi.co/api/v2/type/{type}
   ```

2. **Endpoint detallado:** contiene estadísticas y habilidades tras realizar peticiones HTTP.

   ```http
   GET https://pokeapi.co/api/v2/pokemon/{id}
   ```

Inicialmente se crearon funciones que mantenían una estructura de diccionario similar a esta:

```python
data_dict = {
    "name": "Pokemon",
    "stats": {"hp": 39, "attack": 52, ...},
    "abilities": [{"blaze": "blaze"}, ...],
}
```

Sin embargo, para dejar esta estructura lista para un DataFrame, era necesario aplanarla.

## Recoleccion de toda la data

**Proceso:**

- Itera sobre la lista de Pokémon.
- Aplica la extracción individual a cada elemento.
- Maneja los fallos individuales mediante un `try-catch` sin interrumpir el proceso completo.

## Aplanamiento de Datos

**Problema:** los datos y archivos CSV no manejan bien estructuras anidadas.

Los stats estaban guardados en un diccionario llamado `stats`. La solución fue romper el diccionario y colocar cada stat directamente como una columna separada en la tabla. Es como si tuvieras una carpeta llamada "Calificaciones" con hojas sueltas adentro: en lugar de conservar la carpeta, sacas cada hoja y la pones directamente sobre el escritorio, cada una en su propio lugar.

- **Stats:** `stats.hp` → `hp` (columna directa)

```python
# Antes
pokemon_data["stats"] = {"hp": 39, "attack": 52, "defense": 43}

# Después - Se promocionan al nivel principal
for stat_item in pokemon_data["stats"]:
    stat_name = stat_item["stat"]["name"]
    base_stat = stat_item["base_stat"]
    flat_data[stat_name] = base_stat
```

Para las abilities, la solución fue expandirlas horizontalmente.

Las abilities eran una lista de elementos complejos. Cada ability tenía un nombre, información sobre si era oculta y un número de slot. Se crearon varias columnas: una para el nombre de la primera ability, otra para la segunda y así sucesivamente.

- **Abilities:** array complejo → múltiples columnas (`ability_1_name`, `ability_2_name`, etc.).

```python
# Antes
"abilities": [
    {"name": "blaze", "is_hidden": False, "slot": 1},
    {"name": "solar-power", "is_hidden": True, "slot": 3},
]

# Después - Una columna por cada ability
abilities = extract_abilities(pokemon_data["abilities"])
for i, ability in enumerate(abilities, 1):
    flat_data[f"ability_{i}_name"] = ability["name"]
```

## Manejo de Abilities Variables

**Problema:** los Pokémon tienen diferente cantidad de habilidades.

**Solución:**

```text
# Columnas dinámicas por habilidad
ability_1_name
ability_2_name

# Columnas resumen
all_abilities: "blaze, solar-power"
total_abilities: 2
```

## Organizacion de Columnas

Se estableció un orden lógico:

1. **Identificación:** name, url
2. **Stats de combate:** hp, attack, defense, etc.
3. **Resumen de abilities:** total_abilities, all_abilities
4. **Detalles de abilities:** ability_1_name, ability_2_name, etc.

```text
name -> url -> hp -> attack -> defense -> special-attack -> special-defense -> speed -> total_abilities -> all_abilities -> ability_1_name -> ability_2_name -> ability_3_name -> ...
```

## Data

El Data permite organizar los datos de una manera tabular, lo que beneficia la exportación a CSV.

Con los datos previamente aplanados y las columnas también ordenadas, se utilizó la librería Pandas para crear el Data y poblarla a partir de la lista.

## Exportacion

Para la exportación, se utilizó el método previamente creado y solo fue cuestión de pasarle el nuevo `blob_file`.

## Manejo de Errores

- Peticiones HTTP con `try-catch`.
- Continúa procesando aunque falte un Pokémon.
- Muestra mensajes informativos de progreso.

# Tarea 3: Reportes con Muestreo Aleatorio

Permite al usuario especificar un número máximo de registros aleatorios a incluir en el reporte.

## Frontend

Utilizando la librería Radix UI, se utilizó el componente `label-input` para obtener el tamaño de la muestra desde el lado del cliente.

## Backend

Se modificó el endpoint:

```text
http://{domain}/api/requests/{type}/{sample_size}
```

El endpoint ahora obtiene mediante una variable de path el número de registros requeridos por el usuario. También se modificó el modelo de Pydantic para agregar el campo `sample_size`, que debe ser un número entero mayor o igual a cero (0). Se realizaron los cambios correspondientes en la base de datos y en el procedimiento almacenado para mantener la misma funcionalidad con pequeños ajustes.

## Worker - Azure Function

Mediante la función `get_request(id)` obtenemos un JSON con los datos de la solicitud, incluido el tamaño de la muestra. Validamos si el tamaño deseado es menor que la cantidad de Pokémon disponibles del tipo solicitado. Si es menor, recortamos el arreglo con la lista de Pokémon antes de agregar todos los detalles que usaremos en el Data:

```python
sample_pokemon_list = pokemon_list[:random.randint(1, list_len)]
```

Si el tamaño solicitado por el usuario es mayor que la lista obtenida desde la API de Pokémon, se devuelven todos los Pokémon del mismo tipo que estén disponibles en la API.
